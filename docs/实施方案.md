# E英语宝模块检测智能体 · 实施方案

> 基于《260716 E英语宝模块检测智能体需求》文档分析，目标是用智能体替代人工完成英语宝 APP 的模块内容检测工作，覆盖 Android 与 iOS 双端。

---

## 一、需求理解与现状分析

### 1.1 当前人工检测流程

| 步骤 | 人工操作           | 检测要点                |
| -- | -------------- | ------------------- |
| 1  | 下载正式版/预发布版 APP | —                   |
| 2  | 灰度账号登录         | 账号密码输入、登录成功         |
| 3  | 选择版本年级册、进入模块   | 导航正确                |
| 4  | 检查单元目录文字       | 文字内容正确性             |
| 5  | 进入单元           | —                   |
| 6  | 逐题检查（六项）       | 题干/内容文字/图片/作答/答案/音频 |
| 7  | 进入下一题、验证流程完整性  | 无卡顿、可流转             |
| 8  | 检查报告           | 得分正确、知识性内容正确        |
| 9  | 截图 + TAPD 上报   | 缺陷记录与提交             |

### 1.2 核心痛点

1. **全人工**：流程冗长，每个模块每道题都要逐项核对，耗时巨大
2. **双端差异**：Android 和 iOS 可能出现不同问题，需各测一遍，工作量翻倍
3. **内容比对密集**：题干文字、图片、音频、答案、知识点都要与"脚本"逐一核对
4. **主观判断多**：知识性错误、逻辑错误、图片匹配度等需要语义理解能力

### 1.3 智能体替代的可行性结论

**可行，推荐采用"混合架构"**——结构化自动化负责导航与交互，多模态大模型负责视觉理解与内容语义校验。纯脚本自动化无法胜任（图片匹配、知识性错误判断需语义能力），纯视觉 Agent 又太慢太贵，混合方案兼顾效率与智能。

## 二、技术架构（四层）

### 第一层：测试编排层（Test Orchestration）

- **用例管理**：维护"版本×年级册×模块×单元×题目"的检测矩阵
- **任务调度**：按模块分发检测任务，支持断点续测
- **双端并行**：Android、iOS 任务队列独立调度，并行执行
- **报告汇总**：聚合双端结果，生成检测报告

### 第二层：智能体决策层（AI Agent Core）—— 核心

- **视觉理解模块**：接收 Appium 截图，调用多模态大模型（如 GPT-4o / Claude / GLM-4V）识别屏幕内容
- **推理决策引擎**：Agent Loop——感知→推理→行动→验证，决定下一步操作
- **内容校验引擎**：将屏幕提取内容与脚本数据源比对，输出六项检查结果

### 第三层：自动化执行层（Automation）

- **Appium 2.x**：统一驱动 Android（UiAutomator2）与 iOS（XCUITest）
- **设备集群**：真机/云真机/模拟器，支持多设备并发

### 第四层：数据集成层（Data & Integration）

- **脚本/题库数据源**：每道题的预期内容（题干、图片、音频、正确答案、知识点）—— 校验的"标准答案"
- **TAPD 缺陷上报**：通过 TAPD OpenAPI 自动创建缺陷单
- **截图/日志存储**：OSS/COS 对象存储，留存证据链
- **报告生成**：HTML/Excel 检测报告

## 三、具体实施步骤（四阶段）

### 阶段一：基础搭建（环境与数据准备）

#### Step 1 — 搭建 Appium 自动化底座

- 安装 Appium Server 2.x + UiAutomator2 驱动（Android）+ XCUITest 驱动（iOS）
- 准备测试设备：至少 1 台 Android 真机 + 1 台 iOS 真机（或云真机服务）
- 编写 APP 启动 Capability 配置（包名、Activity、bundleId）
- 验证：能通过脚本启动英语宝 APP 并截图

#### Step 2 — APP 元素结构与无障碍分析

- 用 Appium Inspector 遍历主要页面，梳理元素定位策略
- **关键**：确认题干文字、选项、图片、音频按钮是否有可用的 accessibility id / resource-id
- 若元素可识别 → 用结构化定位（快且准）；若不可识别（如 Canvas/WebView 绘制）→ 依赖视觉理解

#### Step 3 — 打通脚本/题库数据源

- 与内容团队确认"脚本"数据的存储形式（数据库表 / API / Excel）
- 获取每道题的预期数据结构：
  ```
  {
    "question_id": "...",
    "stem_text": "题干预期文字",
    "image_url": "预期图片资源",
    "audio_url": "预期音频资源",
    "correct_answer": "正确答案",
    "knowledge_points": ["知识点1", "知识点2"],
    "listening_text": "听力材料文字（若听力题）"
  }
  ```
- 封装为查询接口，供智能体按 question_id 拉取预期值

#### Step 4 — TAPD OpenAPI 对接

- 申请 TAPD API token，调研缺陷创建接口
- 封装 `create_tapd_bug(title, description, screenshots, severity)` 方法

---

### 阶段二：核心智能体开发

#### Step 5 — 视觉理解模块

- 输入：Appium 截图（PNG）
- 处理：调用多模态大模型，Prompt 指令：
  > "识别这张教育APP题目的屏幕内容，以JSON输出：题干文字、各选项文字、图片描述、是否有音频播放按钮、当前作答状态"
- 输出：结构化 JSON（屏幕实际内容）
- **要点**：对截图做必要的预处理（裁剪题目区域、放大文字）提升识别准确率

#### Step 6 — 推理决策引擎（Agent Loop）

实现核心循环：

```python
while not module_finished:
    screenshot = appium.get_screenshot()
    screen_content = vision_module.extract(screenshot)
    expected = script_source.get(current_question_id)
    check_results = verify_engine.compare(screen_content, expected, checks=6)
    
    if check_results.has_issues():
        report_to_tapd(check_results, screenshot)
    
    # 决策下一步
    action = agent.decide_next(screen_content, module_state)
    appium.execute(action)  # 点击下一题/作答/进入报告
```

#### Step 7 — 内容校验引擎（六项检查映射）

| 检查项        | 人工原文                 | 智能体实现方式                                                |
| ---------- | -------------------- | ------------------------------------------------------ |
| (1) 题干文字   | 题干文字内容是否正确           | OCR/视觉提取题干 → 与脚本 stem_text 比对                          |
| (2) 内容文字   | 是否与脚本相符、完整、无知识/逻辑错误  | 提取题目内容文字 → 比对脚本 → LLM 判断知识性与逻辑性                        |
| (3) 内容图片   | 是否与脚本相符、完整、匹配、无逻辑问题  | 视觉识别图片内容 → 与脚本 image_url 比对 → LLM 判断图文匹配度              |
| (4) 作答验证   | 是否能正常作答、答案能否输入       | Appium 模拟输入/选择/录音 → 检测 UI 反馈是否正常                       |
| (5) 答案与知识点 | 答案是否正确、知识点是否正确       | 答错触发后提取答案/知识点 → 与脚本 correct_answer、knowledge_points 比对 |
| (6) 听力音频   | 是否有且完整、能播放、角色正确、内容相符 | 检测音频控件存在 → 模拟播放验证可播 → 提取音频做 ASR → 与 listening_text 比对  |

#### Step 8 — 导航与流程控制

- 实现"进入模块→单元目录→单元→逐题→报告"的导航状态机
- 每步用视觉+元素双重定位，确保流程可推进
- 检测"卡顿/无法进入下一题"：设置超时 + 重试 + 异常上报

---

### 阶段三：检测流程实现（端到端打通）

#### Step 9 — 登录流程自动化

- Appium 定位账号/密码输入框，输入灰度账号
- 处理登录后的弹窗、引导页

#### Step 10 — 模块与单元导航

- 按检测矩阵遍历"版本×年级册×模块"
- 进入模块后检查单元目录文字（对应人工步骤4）
- 进入单元，开始逐题检测

#### Step 11 — 逐题六项检测（核心循环）

- 对每道题执行 Step 5-7 的检测循环
- 检测完成点击下一题，验证流程完整性（对应步骤6-7）

#### Step 12 — 报告页校验

- 全部答题后进入报告页
- 提取得分 → 与预期分数比对
- 提取报告中的知识性内容 → LLM 校验正确性

#### Step 13 — 缺陷自动上报

- 发现错漏时：截图保存到 COS → 调用 TAPD API 创建缺陷
- 缺陷标题模板：`[模块名][题号][检查项] 问题简述`
- 缺陷内容含：截图链接、实际内容、预期内容、差异说明

---

### 阶段四：双端并行与规模化

#### Step 14 — 双端任务分发

- Android、iOS 各自独立 Appium Session + Agent 实例
- 编排层将检测矩阵拆分，分发给两端并行执行

#### Step 15 — 结果汇总与报告

- 聚合双端检测结果
- 生成检测报告：模块覆盖率、通过率、缺陷清单、截图证据

#### Step 16 — 持续优化

- 收集误报/漏报案例，优化 Prompt 与比对策略
- 对高频固定流程（如登录、导航）固化脚本，减少 LLM 调用以降本提速
- 建立回归基线，版本迭代时快速回归

## 五、关键难点与应对

### 难点 1：图片内容比对

- **问题**：题目图片需与脚本"相符"，但图片无法直接文本比对
- **应对**：
  - 若脚本有图片资源 URL → 下载预期图，与屏幕截图做感知哈希（pHash）相似度比对
  - 若无资源 → 用多模态 LLM 描述图片内容，与脚本文字描述比对
  - 图文匹配度交由 LLM 语义判断

### 难点 2：听力音频校验

- **问题**：需验证音频"有、完整、能播、角色对、内容符"
- **应对**：
  - 有/能播：检测音频控件 + 模拟点击播放 + 检测播放状态
  - 完整/内容符：抓取音频文件（抓包/APP 沙箱提取）→ ASR 转文字 → 与 listening_text 比对
  - 角色设置：从音频元数据或接口响应中提取角色信息

### 难点 3：口语题录音作答

- **问题**：需模拟录音作答
- **应对**：Appium 模拟麦克风权限授予 + 注入预录音频文件代替实时录音

### 难点 4：知识性/逻辑错误判断

- **问题**：需语义理解，非简单比对
- **应对**：构造专项 Prompt，让 LLM 扮演学科教师，对题目内容做知识性与逻辑性审查

### 难点 5：成本与速度

- **问题**：每题都调多模态 LLM，成本高、速度慢
- **应对**：
  - 分层策略：固定流程用脚本（登录/导航），仅内容校验调 LLM
  - 缓存：相同截图不重复识别
  - 批处理：多个检查项合并到一次 LLM 调用

## 七、风险提示

1. **脚本数据源是前提**：若无结构化脚本数据，校验引擎无法工作——需优先与内容团队确认数据可用性
2. **多模态 LLM 准确率**：复杂图片/特殊排版可能误识别，需建立人工抽检机制
3. **iOS 自动化限制**：XCUITest 在某些场景不如 Android 灵活，需预留适配成本
4. **灰度账号与预发布包**：需保证自动化环境能稳定获取预发布包并登录灰度环境
5. **成本可控性**：LLM 调用费用随题目量线性增长，需做成本测算与预算控制
